
# 🔐 SPRING SECURITY — WHAT IT CAN SOLVE AND WHAT IT CANNOT SOLVE

# 1. 🟢 WHAT IS SPRING SECURITY?

Spring Security is a Java security framework used to protect Spring applications.

Its main responsibilities are:

1. Authentication — Who are you?
2. Authorization — What are you allowed to do?
3. Request protection — Which HTTP requests can access which resources?
4. Security integration — How does your application validate credentials, tokens, and sessions?
5. Security protections — How can your application defend against common web attacks?

⚠️ IMPORTANT:

Spring Security is NOT a complete cybersecurity solution.

It protects specific parts of your application. You must implement other security controls yourself.

---

# 2. 🟢 WHAT SPRING SECURITY CAN SOLVE

## 🔐 1. Authentication

🟢 CAN SOLVE

Authentication means verifying the identity of a user.

Spring Security can:

- Authenticate users using username and password.
- Authenticate users using a database.
- Integrate with custom UserDetailsService.
- Validate credentials using PasswordEncoder.
- Support authentication through JWT bearer tokens.
- Integrate with OAuth 2.0 and OpenID Connect.
- Support multi-factor authentication through custom integrations.
- Support session-based authentication.
- Support LDAP authentication.
- Integrate with external identity providers.

Example:

User sends:

POST /login

{
  "username": "john",
  "password": "mypassword"
}

Spring Security can verify the credentials and establish an authenticated identity.

⚠️ IMPORTANT:

Spring Security does not automatically create your entire registration, login, email verification, or password recovery business logic.

You must implement the appropriate application workflows.

---

## 🔐 2. Password Hashing and Password Verification

🟢 CAN SOLVE

Spring Security provides PasswordEncoder.

It can:

- Hash passwords before storing them.
- Verify passwords during login.
- Support BCrypt.
- Support Argon2 when the required implementation is available.
- Support PBKDF2 and other supported password encoders.
- Support DelegatingPasswordEncoder for multiple encoding formats.

Example:

@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder();
}

Hash password:

String encodedPassword =
    passwordEncoder.encode("mypassword");

Verify password:

boolean matches =
    passwordEncoder.matches("mypassword", encodedPassword);

⚠️ IMPORTANT:

Never store plain-text passwords.

Spring Security hashes passwords, but you must make sure your registration and password update code actually uses the PasswordEncoder.

Password hashing does not prevent:

- Weak passwords.
- Credential stuffing.
- Password reuse.
- Phishing.
- Users sharing their passwords.

Use additional controls such as MFA, password policies, and login rate limiting.

---

## 🔐 3. Authorization and Role-Based Access Control (RBAC)

🟢 CAN SOLVE

Authorization determines what an authenticated user can access.

Spring Security supports:

- Role-based access control.
- Authority-based access control.
- URL-level authorization.
- Method-level authorization.
- Custom authorization rules.
- Access-denied handling.

Example:

.requestMatchers("/admin/**").hasRole("ADMIN")
.requestMatchers("/user/**").hasAnyRole("USER", "ADMIN")
.requestMatchers("/public/**").permitAll()

Method-level security:

@EnableMethodSecurity

@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    // Delete user
}

Spring Security can prevent a normal user from accessing an admin endpoint.

⚠️ IMPORTANT:

Authentication does not mean authorization.

A user can be successfully authenticated but still not have permission to access a resource.

---

## 🔐 4. JWT Validation

🟢 CAN SOLVE

Spring Security can validate JWT bearer tokens using its OAuth2 Resource Server support.

It can verify:

- Token signature.
- Token expiration.
- Not-before timestamp.
- Issuer, when configured.
- Audience, when configured.
- Required authorities and scopes, through appropriate configuration and conversion.

Example configuration:

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http)
        throws Exception {

    http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/public/**").permitAll()
            .anyRequest().authenticated()
        )
        .oauth2ResourceServer(oauth2 ->
            oauth2.jwt(Customizer.withDefaults())
        );

    return http.build();
}

⚠️ IMPORTANT:

JWT validation does not automatically mean that every token is safe.

You must configure trusted issuers, signing keys, algorithms, and relevant claims correctly.

Also:

- JWT payloads are normally encoded, not encrypted.
- Do not put passwords or sensitive secrets inside JWT claims.
- Do not accept unsigned tokens.
- Do not trust a JWT just because it has three sections separated by dots.

---

## 🔐 5. URL and Endpoint Protection

🟢 CAN SOLVE

Spring Security can protect API endpoints.

Example:

.requestMatchers("/api/public/**").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/user/**").authenticated()

It can prevent unauthorized users from accessing protected routes.

Example:

GET /api/admin/users

If the user does not have the required authority, Spring Security can deny access.

⚠️ IMPORTANT:

Protecting an Angular route is not enough.

Angular route guards only control frontend navigation.

Backend authorization must independently protect every sensitive API endpoint.

---

## 🔐 6. Method-Level Security

🟢 CAN SOLVE

Spring Security can protect individual service methods.

Example:

@PreAuthorize("hasAuthority('USER_DELETE')")
public void deleteUser(Long userId) {
    // Delete user
}

Other useful annotations:

@Secured("ROLE_ADMIN")

@RolesAllowed("ADMIN")

@PreAuthorize("hasRole('ADMIN')")

@PostAuthorize("returnObject.owner == authentication.name")

⚠️ IMPORTANT:

Method security must be enabled and correctly configured.

Also, method security does not automatically solve every resource ownership problem.

---

## 🔐 7. CSRF Protection

🟢 CAN HELP SOLVE

CSRF means Cross-Site Request Forgery.

An attacker may trick a logged-in user's browser into sending an unwanted request.

Spring Security provides CSRF protection.

Example:

http.csrf(Customizer.withDefaults());

Spring Security can:

- Generate and validate CSRF tokens.
- Protect state-changing requests.
- Integrate CSRF tokens with browser-based applications.
- Support cookie-based CSRF token repositories.

⚠️ IMPORTANT:

CSRF protection depends on how authentication credentials are transported.

If you authenticate using automatically attached cookies, CSRF protection is important.

If you use explicit Authorization bearer tokens that are not automatically attached by the browser, the CSRF risk is different.

Do not blindly disable CSRF without understanding your authentication architecture.

---

## 🔐 8. Session Management

🟢 CAN SOLVE

Spring Security can manage authenticated sessions.

It supports:

- Session creation policies.
- Session invalidation.
- Session fixation protection.
- Concurrent session controls.
- Session expiration configuration.
- Security context management.

Example:

.sessionManagement(session -> session
    .sessionCreationPolicy(SessionCreationPolicy.STATELESS)
)

⚠️ IMPORTANT:

STATELESS is generally used for bearer-token APIs.

It is not a universal setting for every application.

If you use cookie-based sessions, configure session management appropriately.

---

## 🔐 9. Logout and Session Invalidation

🟢 CAN SOLVE

Spring Security supports logout handling.

Example:

.logout(logout -> logout
    .logoutUrl("/logout")
    .invalidateHttpSession(true)
    .clearAuthentication(true)
)

It can invalidate the server-side session and clear authentication information.

⚠️ IMPORTANT:

For JWT authentication, logging out does not automatically invalidate an already issued stateless JWT.

You may need:

- Short-lived access tokens.
- Refresh-token revocation.
- Token denylisting, if required.
- Server-side token/session management.

---

## 🔐 10. Security Headers

🟢 CAN HELP SOLVE

Spring Security supports several HTTP security headers.

Examples include:

- X-Content-Type-Options.
- Cache-Control.
- Strict-Transport-Security.
- X-Frame-Options.
- Content-Security-Policy, when configured.

Example:

http.headers(headers -> headers
    .contentTypeOptions(Customizer.withDefaults())
    .frameOptions(frame -> frame.deny())
    .httpStrictTransportSecurity(hsts -> hsts
        .includeSubDomains(true)
        .maxAgeInSeconds(31536000)
    )
);

⚠️ IMPORTANT:

Not every security header is automatically configured for every application or deployment.

You must review and configure headers according to your requirements.

A Content Security Policy must be designed carefully. A weak policy may not provide meaningful XSS protection.

---

## 🔐 11. CORS Configuration

🟢 CAN SOLVE THE BROWSER CORS CONFIGURATION PROBLEM

Spring Security can integrate with Spring MVC CORS configuration.

Example:

http.cors(Customizer.withDefaults());

You can configure allowed origins, methods, and headers.

Example:

@Configuration
public class CorsConfig {

    @Bean
    CorsConfigurationSource corsConfigurationSource() {

        CorsConfiguration config =
            new CorsConfiguration();

        config.setAllowedOrigins(
            List.of("https://myfrontend.com")
        );

        config.setAllowedMethods(
            List.of("GET", "POST", "PUT", "DELETE")
        );

        config.setAllowedHeaders(
            List.of("Authorization", "Content-Type")
        );

        config.setAllowCredentials(false);

        UrlBasedCorsConfigurationSource source =
            new UrlBasedCorsConfigurationSource();

        source.registerCorsConfiguration("/**", config);

        return source;
    }
}

⚠️ CRITICAL:

CORS is NOT authentication.

CORS is NOT authorization.

CORS does NOT prevent Postman, curl, backend scripts, or other non-browser clients from calling your API.

An attacker can send requests outside the browser and can forge an Origin header.

Never use CORS as your main API security mechanism.

## 🔐 12. Access Denied and Authentication Failure Handling

🟢 CAN SOLVE

Spring Security supports handling authentication and authorization failures.

Examples:

- AuthenticationEntryPoint.
- AccessDeniedHandler.
- AuthenticationFailureHandler.
- AuthenticationSuccessHandler.

Typical HTTP responses:

401 Unauthorized:
User is not authenticated or valid authentication is missing.

403 Forbidden:
User is authenticated but does not have permission.

⚠️ IMPORTANT:

A 401 and 403 response should be used consistently.

Do not expose passwords, tokens, stack traces, or sensitive internal information in error messages.

## 🔐 13. OAuth 2.0 and OpenID Connect Integration

🟢 CAN HELP SOLVE

Spring Security supports OAuth 2.0 and OpenID Connect integrations.

It can support:

- OAuth 2.0 login.
- OpenID Connect login.
- OAuth 2.0 resource servers.
- OAuth 2.0 client functionality.
- JWT and opaque-token authentication.
- Integration with external identity providers.

Examples of identity providers:

- Keycloak.

- Auth0.
- Microsoft Entra ID.

⚠️ IMPORTANT:

Spring Security provides integration and protocol support.

It does not automatically configure your identity provider, registration policies, MFA policies, or business-specific account management.

# 3. 🔴 WHAT SPRING SECURITY CANNOT SOLVE ALONE

These are important security problems that require additional application code, infrastructure controls, or other security tools.

## 🔴 1. SQL Injection

Spring Security does NOT automatically prevent SQL injection.

Example of vulnerable code:

String sql =
    "SELECT * FROM users WHERE username = '"
    + username + "'";

An attacker may manipulate the input to change the SQL query.

Protection:

- Use PreparedStatement.
- Use parameterized queries.
- Use JPA repositories correctly.
- Avoid building SQL using untrusted input.
- Validate input where appropriate.

Example:

@Query("SELECT u FROM User u WHERE u.username = :username")
Optional<User> findByUsername(
    @Param("username") String username
);

⚠️ Spring Security protects authentication and authorization.

SQL injection prevention belongs primarily to secure database access and coding practices.

---

## 🔴 2. Cross-Site Scripting (XSS)

Spring Security does NOT automatically make all frontend and backend output safe from XSS.

XSS happens when an attacker injects malicious JavaScript into a page.

Example:

<script>
    alert('XSS');
</script>

Protection:

- Use Angular's built-in template escaping.
- Avoid unsafe HTML insertion.
- Avoid bypassSecurityTrustHtml unless absolutely necessary.
- Sanitize untrusted HTML using an appropriate sanitizer.
- Configure a strong Content Security Policy.
- Avoid placing sensitive tokens in JavaScript-accessible storage.

⚠️ HttpOnly cookies prevent JavaScript from reading the cookie directly, but XSS can still perform actions through the victim's browser.

---

## 🔴 3. Brute Force Attacks

Spring Security does NOT automatically provide complete login rate limiting.

An attacker may repeatedly attempt passwords.

Protection:

- Rate limit login requests.
- Introduce temporary account lockouts carefully.
- Add CAPTCHA or risk-based challenges where appropriate.
- Monitor repeated failures.
- Use MFA.
- Detect suspicious login patterns.

Possible tools:

- Bucket4j.
- Redis-based rate limiting.
- API gateway rate limiting.
- Web application firewall.

⚠️ Do not rely only on account lockouts because attackers may abuse them to lock legitimate users out.

---

## 🔴 4. Credential Stuffing

Spring Security does NOT automatically stop attackers from testing leaked username/password combinations.

Protection:

- MFA.
- Rate limiting.
- Breached-password checks.
- Suspicious login detection.
- Login alerts.
- Bot detection.

---

## 🔴 5. Password Reset and Account Recovery Abuse

Spring Security does NOT automatically implement a secure password recovery workflow.

You must implement:

- Secure reset-token generation.
- Cryptographically strong random tokens.
- Short token expiration.
- One-time token usage.
- Server-side token validation.
- Rate limiting.
- Secure email delivery.
- Session invalidation after password changes where appropriate.

⚠️ Never use predictable password reset tokens.

---

## 🔴 6. IDOR (Insecure Direct Object Reference)

Spring Security does NOT automatically know whether a user owns a particular database record.

Example:

GET /api/orders/100

A user changes the ID:

GET /api/orders/101

If order 101 belongs to another user, the application must deny access.

Protection:

Check ownership in the service layer.

Example:

Order order = orderRepository
    .findById(orderId)
    .orElseThrow();

if (!order.getUser().getId()
        .equals(currentUserId)) {
    throw new AccessDeniedException(
        "Access denied"
    );
}

⚠️ IMPORTANT:

Being authenticated does not mean a user can access every record.

This is one of the most important application-level security responsibilities.

---

## 🔴 7. Business Logic Vulnerabilities

Spring Security cannot automatically understand your application's business rules.

Examples:

- Applying the same discount multiple times.
- Buying an item for a manipulated price.
- Withdrawing more money than the available balance.
- Approving your own request when approval should require another user.
- Skipping mandatory workflow steps.

Protection:

- Validate business rules in the backend.
- Verify prices and totals on the server.
- Check transaction states.
- Enforce approval workflows.
- Validate ownership and permissions.
- Use database transactions where appropriate.

---

## 🔴 8. Mass Assignment

Spring Security does NOT automatically prevent users from modifying fields they should not control.

Example:

{
  "name": "John",
  "role": "ADMIN",
  "accountEnabled": true
}

If your backend directly maps this request to an entity, a user might change protected fields.

Protection:

- Use request DTOs.
- Explicitly map permitted fields.
- Never blindly bind request data to sensitive entities.
- Perform authorization checks on sensitive changes.

---

## 🔴 9. Server-Side Request Forgery (SSRF)

Spring Security does NOT automatically prevent SSRF.

SSRF happens when an attacker tricks your backend into making requests to unintended internal or external destinations.

Example:

Your backend downloads a URL provided by the user.

An attacker supplies an internal address instead of a public website.

Protection:

- Use destination allowlists.
- Block private and internal IP ranges where appropriate.
- Validate DNS resolution and redirects.
- Restrict outbound network access.
- Avoid arbitrary user-controlled URLs.

---

## 🔴 10. File Upload Attacks

Spring Security does NOT automatically make file uploads safe.

Possible attacks:

- Malicious executable uploads.
- HTML uploads.
- Path traversal.
- Malware uploads.
- Extremely large uploads.
- Files with misleading extensions.

Protection:

- Validate file size.
- Validate actual file type, not just extension.
- Generate server-side filenames.
- Store uploads outside executable web directories.
- Restrict file permissions.
- Scan files where appropriate.
- Prevent path traversal.
- Use safe download headers.

---

## 🔴 11. Path Traversal

Spring Security does NOT automatically protect every file access operation.

Example:

../../../../etc/passwd

Protection:

- Normalize file paths.
- Restrict access to a fixed directory.
- Reject traversal sequences where appropriate.
- Do not trust user-controlled filesystem paths.
- Check that the resolved file remains inside the permitted directory.

---

## 🔴 12. Insecure Deserialization

Spring Security does NOT automatically make unsafe Java deserialization safe.

Protection:

- Avoid deserializing untrusted Java objects.
- Prefer simple DTOs and safe formats.
- Validate incoming data.
- Use secure serialization libraries and configurations.
- Keep dependencies updated.

---

## 🔴 13. XML External Entity (XXE)

Spring Security does NOT automatically secure every XML parser.

Protection:

- Disable external entities.
- Disable external DTD processing.
- Use secure XML parser configurations.
- Avoid parsing untrusted XML where possible.

---

## 🔴 14. Denial of Service (DoS)

Spring Security does NOT automatically prevent all DoS or DDoS attacks.

Protection:

- API rate limiting.
- Request-size limits.
- Connection limits.
- Timeouts.
- Reverse proxies.
- WAF.
- Load balancers.
- Infrastructure-level DDoS protection.
- Resource monitoring.

---

## 🔴 15. Dependency Vulnerabilities

Spring Security does NOT automatically make vulnerable dependencies safe.

Protection:

- Keep Spring Boot and Spring Security updated.
- Scan dependencies.
- Monitor CVEs.
- Remove unused dependencies.
- Use trusted repositories.
- Review security advisories.

Tools:

- OWASP Dependency-Check.
- Snyk.
- GitHub Dependabot.
- Software composition analysis tools.

---

## 🔴 16. Infrastructure and Server Security

Spring Security does NOT secure your entire server or cloud infrastructure.

It does not automatically protect:

- Operating system vulnerabilities.
- Exposed database ports.
- Cloud storage permissions.
- Server SSH access.
- Container vulnerabilities.
- Kubernetes configuration.
- Firewall rules.
- Network segmentation.
- TLS certificate deployment.

Protection requires infrastructure and deployment security.

---

## 🔴 17. Man-in-the-Middle Attacks (MITM)

Spring Security does NOT replace HTTPS.

Protection:

- Use HTTPS everywhere.
- Use valid TLS certificates.
- Redirect HTTP to HTTPS.
- Configure secure TLS versions.
- Configure HSTS.
- Secure internal service communication.

⚠️ Never send passwords or bearer tokens over unencrypted HTTP in production.

---

## 🔴 18. JWT Theft and Token Replay

Spring Security can validate JWTs, but it cannot automatically stop someone from replaying a valid stolen bearer token.

Example:

An attacker steals:

Authorization: Bearer eyJhbGciOi...

The attacker sends that same token from Postman.

If the token is valid and not expired, the backend may accept it.

Protection:

- Use short-lived access tokens.
- Protect refresh tokens.
- Rotate refresh tokens.
- Revoke refresh tokens when necessary.
- Use secure token storage.
- Consider a Backend-for-Frontend (BFF).
- Consider proof-of-possession mechanisms such as DPoP where supported and appropriate.

⚠️ IMPORTANT:

A normal bearer JWT is usable by whoever possesses it.

Spring Security validates the token; it does not prove that the request came from the original browser.

---

## 🔴 19. Protecting JWTs Stored in localStorage

Spring Security cannot prevent JavaScript running in your Angular application from reading a JWT stored in localStorage.

Example:

localStorage.getItem("access_token");

An attacker who successfully executes JavaScript through XSS may be able to steal the token.

Possible architecture:

Angular Browser
      |
      | Secure HttpOnly Cookie
      v
Spring Boot BFF
      |
      | Server-side access token
      v
Protected Backend API

Benefits:

- JavaScript cannot directly read an HttpOnly cookie.
- Access tokens can remain on the server.
- The browser does not need to store a JWT in localStorage.

⚠️ IMPORTANT:

HttpOnly cookies do not prevent every attack.

Cookie-based authentication requires appropriate CSRF protection, Secure and SameSite settings, and careful session management.

A stolen session cookie may still be replayed.

---

## 🔴 20. Preventing Postman or curl Access

Spring Security cannot guarantee that API requests originate from your Angular application.

Example:

Angular:
GET /api/users

Postman:
GET /api/users

Both can send HTTP requests to your backend.

The backend should decide whether the request is authenticated and authorized.

Protection:

- Validate authentication on every protected endpoint.
- Enforce authorization on every protected operation.
- Use short-lived tokens.
- Protect refresh tokens.
- Consider a BFF architecture.
- Use rate limiting and abuse detection.

⚠️ IMPORTANT:

CORS does not block Postman.

Origin and Referer headers are not reliable proof of browser identity.

There is no reliable way to guarantee that a request came from your own frontend merely by checking its headers.

# 4. 🟡 ATTACKS SPRING SECURITY CAN HELP WITH, BUT NOT COMPLETELY SOLVE

| Attack | Spring Security's role |
|---|---|
| Brute force | Authentication integration; rate limiting needs additional controls |
| Credential stuffing | Authentication integration; detection and throttling need additional controls |
| CSRF | Provides CSRF token protection |
| XSS | Some security headers; output encoding and frontend protections are still needed |
| Clickjacking | Supports frame-related security headers |
| Session fixation | Provides session fixation protection |
| Session hijacking | Helps manage sessions; cannot prevent every form of theft |
| JWT replay | Validates JWTs; does not automatically prevent replay |
| IDOR | Supports authorization; ownership checks need application logic |
| Privilege escalation | Supports role and authority checks; correct permissions must be designed |
| CORS misuse | Provides CORS integration; does not authenticate API callers |
| OAuth attacks | Provides protocol support; secure configuration and identity-provider controls remain necessary |
| Account takeover | Provides authentication mechanisms; additional detection and MFA are needed |

# 5. 🟢 WHAT EACH SECURITY LAYER SHOULD HANDLE

A secure application needs multiple layers.

## Layer 1: Angular Frontend

Responsibilities:

- Safe rendering of user input.
- Avoid unsafe HTML insertion.
- Frontend route guards for user experience.
- Avoid storing sensitive tokens in JavaScript-accessible storage when possible.
- Avoid exposing secrets in frontend code.
- Use HTTPS.
- Handle authentication errors safely.

⚠️ Angular route guards are NOT backend security.

## Layer 2: Spring Security

Responsibilities:

- Authentication.
- Authorization.
- JWT validation.
- Session management.
- CSRF protection.
- Security filter chain.
- Security headers.
- CORS integration.
- Authentication failure handling.

## Layer 3: Spring Boot Application Code

Responsibilities:

- IDOR prevention.
- Business logic validation.
- DTO validation.
- SQL injection prevention through safe database access.
- File upload validation.
- Password reset logic.
- Account ownership checks.
- Transaction validation.
- Safe error handling.

## Layer 4: Database

Responsibilities:

- Least-privilege database accounts.
- Secure credentials.
- Parameterized queries.
- Database access restrictions.
- Backups.
- Encryption where appropriate.
- Database auditing.

## Layer 5: Infrastructure

Responsibilities:

- HTTPS/TLS.
- Firewall.
- WAF.
- DDoS protection.
- Reverse proxy.
- Rate limiting.
- Server hardening.
- Container security.
- Secret management.
- Monitoring and alerting.

# 6. 🔵 EXAMPLE: WHAT SPRING SECURITY CAN PROTECT

Consider these endpoints:

GET    /api/public/products
GET    /api/user/profile
GET    /api/admin/users
DELETE /api/admin/users/{id}

A Spring Security configuration could look like:

@Configuration
@EnableMethodSecurity
public class SecurityConfig {

    @Bean
    SecurityFilterChain securityFilterChain(
            HttpSecurity http) throws Exception {

        http
            .authorizeHttpRequests(auth -> auth

                .requestMatchers("/api/public/**")
                    .permitAll()

                .requestMatchers("/api/admin/**")
                    .hasRole("ADMIN")

                .requestMatchers("/api/user/**")
                    .hasAnyRole("USER", "ADMIN")

                .anyRequest()
                    .authenticated()
            )

            .oauth2ResourceServer(oauth2 ->
                oauth2.jwt(Customizer.withDefaults())
            );

        return http.build();
    }
}

This is an illustrative bearer-JWT configuration.

⚠️ IMPORTANT:

- Configure the JWT issuer, signing keys, and other required validation.
- Configure CSRF according to your authentication mechanism.
- Configure CORS separately.
- Use HTTPS.
- Add resource ownership checks in application services.
- Add rate limiting separately.
- Do not assume this configuration alone makes the application production-secure.

# 7. 🔴 COMMON MISUNDERSTANDINGS

❌ WRONG: If I use Spring Security, my application is completely secure.

✅ CORRECT: Spring Security handles important security responsibilities, but application and infrastructure security are also required.

❌ WRONG: CORS prevents Postman from calling my API.

✅ CORRECT: CORS is a browser security mechanism. Non-browser clients can call APIs directly.

❌ WRONG: JWT means nobody can steal or reuse my token.

✅ CORRECT: A stolen bearer token can generally be replayed until it expires or is otherwise invalidated.

❌ WRONG: If a user is authenticated, they can access every API.

✅ CORRECT: Authentication and authorization are different.

❌ WRONG: @PreAuthorize automatically prevents IDOR.

✅ CORRECT: You must check whether the authenticated user is allowed to access the specific resource.

❌ WRONG: Disabling CSRF is always safe for JWT applications.

✅ CORRECT: It depends on how credentials are sent. Cookie-based authentication generally needs CSRF protection.

❌ WRONG: HttpOnly cookies prevent all XSS attacks.

✅ CORRECT: They prevent JavaScript from reading the cookie directly, but malicious JavaScript may still perform actions through the browser.

❌ WRONG: Spring Security automatically rate-limits login attempts.

✅ CORRECT: Implement or integrate a rate-limiting solution.

# 8. 🟢 PRODUCTION SECURITY CHECKLIST

## Authentication

[ ] Passwords are hashed using a strong password encoder.
[ ] Login errors do not expose sensitive information.
[ ] Login attempts are rate-limited.
[ ] MFA is enabled where appropriate.
[ ] Password reset tokens are secure and short-lived.
[ ] Account recovery is protected.

## Authorization

[ ] Every protected API requires authentication.
[ ] Admin endpoints require appropriate privileges.
[ ] Method-level authorization is configured where needed.
[ ] Users can only access resources they are permitted to access.
[ ] IDOR checks are implemented.
[ ] Sensitive operations are authorized on the backend.

## JWT and Session Security

[ ] JWT signatures are validated.
[ ] JWT expiration is checked.
[ ] Issuer and audience are validated where applicable.
[ ] Signing keys are securely managed.
[ ] Access tokens have appropriate lifetimes.
[ ] Refresh tokens are protected and rotated where appropriate.
[ ] Logout and token revocation behavior is understood.
[ ] Token storage and transport are secure.

## Browser Security

[ ] HTTPS is enforced.
[ ] CORS allows only intended origins.
[ ] CSRF protection matches the authentication architecture.
[ ] Security headers are configured.
[ ] XSS protections are implemented.
[ ] Sensitive tokens are not unnecessarily exposed to JavaScript.

## Backend Security

[ ] SQL queries use parameterized access.
[ ] Input validation is implemented.
[ ] DTOs prevent mass assignment.
[ ] File uploads are validated.
[ ] SSRF protections are implemented where URLs are fetched.
[ ] Business rules are validated server-side.
[ ] Sensitive errors and stack traces are not exposed.

## Infrastructure

[ ] Dependencies are updated and scanned.
[ ] Database access is restricted.
[ ] Secrets are not committed to source control.
[ ] Servers and containers are hardened.
[ ] Rate limiting and monitoring are enabled.
[ ] Backups and recovery procedures are tested.

## ⭐ THE MOST IMPORTANT CONCEPT

Spring Security protects the identity and permissions of requests.

Your application code protects your business data and business rules.

Your infrastructure protects the environment in which your application runs.

You need all three to build a secure application.
