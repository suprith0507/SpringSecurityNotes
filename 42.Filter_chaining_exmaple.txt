🟦 SECURITY CONFIGURATION
════════════════════════════════════════════════════════════════════════════════════════════════════

@Bean
public SecurityFilterChain securityFilterChain(
        HttpSecurity http)
        throws Exception {

    return http

        .csrf(Customizer.withDefaults())

        .cors(Customizer.withDefaults())

        /*
        RateLimit First
        */
        .addFilterBefore(
                rateLimitFilter,
                UsernamePasswordAuthenticationFilter.class)

        /*
        Brute Force After RateLimit
        */
        .addFilterBefore(
                bruteForceFilter,
                UsernamePasswordAuthenticationFilter.class)

        /*
        JWT Before UsernamePasswordAuthenticationFilter
        */
        .addFilterBefore(
                jwtAuthenticationFilter,
                UsernamePasswordAuthenticationFilter.class)

        .authorizeHttpRequests(auth ->
                auth.anyRequest()
                        .authenticated())

        .build();
}

🟥 WHY RATELIMIT FILTER IS PLACED BEFORE JWT?
════════════════════════════════════════════════════════════════════════════════════════════════════

Rate limiting is extremely cheap.

JWT validation is expensive.

JWT validation requires:

Token parsing

Signature verification

Claims extraction

Cryptographic verification


Suppose

10000 requests/sec

from attacker.

If JWT runs first:

10000 JWT validations/sec

CPU Waste.


Better:

Request
  │
  ▼
RateLimitFilter

Too many requests?

 ┌──────────┐
 │ YES      │
 └────┬─────┘
      ▼

429 Too Many Requests

NO JWT Parsing Needed.


Flow

Request
   │
   ▼
RateLimitFilter
   │
   ▼
Allowed ?
   │
   ▼
JWT Filter

STATEFUL APPLICATIONS

(Session + Cookies)

   │
   ▼
CSRF Filter
   │
   ▼
Valid CSRF Token?
   │
   ▼

Why?

Even authenticated users can be victims of CSRF attack.

CSRF protection must happen before business logic.

For JWT Stateless APIs

🏆 INTERVIEW ANSWER
════════════════════════════════════════════════════════════════════════════════════════════════════

RateLimitFilter is placed before JWT because rejecting excessive traffic is cheaper than JWT validation.

BruteForceFilter is placed before authentication because blocked users/IPs should be stopped before database lookups.

JWTAuthenticationFilter is placed before UsernamePasswordAuthenticationFilter because JWT requests already contain authentication information. The JWT filter validates the token and populates SecurityContextHolder before Spring Security's authentication filters execute.

AuthorizationFilter always comes after authentication because Spring cannot decide what resources a user can access until it knows who the user is.

Authentication → SecurityContextHolder Population → Authorization is the core order followed by Spring Security.
