Generally NOT recommended.

Service layer should remain independent of HTTP.

BAD:

@Service
public class CustomerService {

   public void save(
      HttpServletRequest request){

   }
}

Reason:

Service becomes tightly coupled to web layer.

══════════════════════════════════════════════════════════════════════════════════

Preferred:

Controller extracts data.

@GetMapping
public void save(
       HttpServletRequest request){

    String user =
       request.getUserPrincipal().getName();

    service.save(user);
}

Service remains clean.

@Service
public void save(String user){

}

BUT IF REALLY NEEDED

Spring stores request internally in ThreadLocal.

You can access it anywhere:

ServletRequestAttributes attrs =
   (ServletRequestAttributes)
   RequestContextHolder.getRequestAttributes();

HttpServletRequest request =
   attrs.getRequest();

Example:

@Service
public class TestService {

    public void execute() {

        HttpServletRequest request =
           ((ServletRequestAttributes)
            RequestContextHolder
            .getRequestAttributes())
            .getRequest();
    }
}

Works because request is bound to current thread.

KEY INTERVIEW POINT:
HttpServletRequest and HttpServletResponse are the primary entry and exit abstractions of the Servlet API. They are created by the servlet container (Tomcat) from raw HTTP network traffic and travel through the entire Spring Security filter chain, DispatcherServlet, controllers, and back. The same objects are reused throughout the request lifecycle. Controller return values never directly become network responses; Spring MVC converts them through HandlerAdapters and HttpMessageConverters into the existing HttpServletResponse, which Tomcat finally serializes into raw HTTP packets and sends to the client.
